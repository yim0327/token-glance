# 개발 기록

Token Glance를 어떤 필요에서 출발해 어떤 순서로 만들었는지, 실제로 쓰면서 발견한 문제를 어떻게
고쳤는지 정리합니다. 요구사항은 [PRD](PRD.md), 측정 조건과 수치는 [성능 기록](perf.md), 현재
상태는 [진행 상황](PROGRESS.md)에 있습니다.

## 1. 출발점과 초기 제약

작성자는 Claude Code와 Codex CLI를 구독 플랜으로 함께 씁니다. 남은 한도를 보려면 도구마다
터미널에서 `/usage`나 `/status`를 따로 확인해야 했습니다. 두 도구의 남은 %와 초기화 시각을
메뉴바에 나란히 보고 싶었던 것이 출발점입니다.

첫 커밋에 들어간 PRD 초안(v0.4)은 작성자가 AI 코딩 도구 Claude Code와 대화하며 만들었습니다.
작성자가 정한 것은 두 가지입니다.

- 화면에 보여줄 내용
- 프라이버시 원칙: 프롬프트·응답을 저장하지 않고, 기본 설정에서는 네트워크 호출을 하지 않으며,
  인증 정보를 직접 읽지 않습니다.

성능 목표는 AI가 제안한 수치를 작성자가 받아들였습니다. idle CPU 1% 미만, 메모리 50MB 미만, 증분
갱신 200ms 미만, 훅 20ms 이하입니다.

처음부터 있던 제약은 다음과 같습니다.

- 구독 한도는 %로만 노출됩니다. Claude Code 로컬 로그에는 %가 없어서 statusline 훅으로 받습니다.
- 로그와 훅 입력의 형식은 공개된 규격이 아닙니다. 그래서 가정을 실제 로컬 데이터로 먼저 확인하고
  [log-schemas.md](log-schemas.md)에 기록한 뒤에 구현했습니다.
- Apple Developer 계정이 없어서 ad-hoc 서명, 미공증, arm64 전용으로 배포합니다.
- `~/.claude/settings.json`은 사용자 동의와 백업을 거친 뒤에만 바꿉니다.

[PRD §12](PRD.md#12-마일스톤)에 있습니다.

## 3. 문제 해결 사례

### 사례 1. Codex 사용량 갱신 누락 ([#1](https://github.com/yim0327/token-glance/pull/1), [#3](https://github.com/yim0327/token-glance/pull/3))

**문제.** 작성자가 Codex 사용 중에 메뉴바 값이 바뀌지 않는 것을 발견했습니다. AI가 시각과 바이트
수만 기록하는 probe로 원인을 진단했습니다. Codex는 rollout 파일을 열어 둔 채 덧붙이는데, 이 기기의
FSEvents는 파일 생성만 알렸습니다. 그래서 값이 36초 뒤 5분 폴링 때에야 반영됐습니다. 1차 수정 후
작성자가 새 세션과 재시작 후 재개한 세션에서 다시 누락을 발견했고, 두 경우를 직접 재현했습니다.

**선택 근거.** 최근 커진 rollout만 2초마다 `stat`으로 크기를 비교하고, 크기가 바뀐 경우에만 기존
증분 읽기를 실행합니다. 전체 재파싱은 하지 않습니다. 2차 수정에서 감시 대상을 넓혔습니다. 첫 스캔
이후 생긴 파일과 24시간 안에 수정된 rollout도 포함합니다.

**검증 결과.**

- 자동 테스트: `ActiveFileSetTests`의 회귀 테스트 2개가 수정 전 코드에서 실패하는 것을
  확인했습니다. `IncrementalIndexTests.swift`에서는 첫 동기화 뒤 생긴 세션을 무작위 20가지로 나눠
  덧붙여도 전체 파싱과 결과가 같은지 확인합니다.
- 실사용 측정(반영 시간):
  - 2차 수정 후: 새 세션 0.03초, 최근 세션 1.4초, 재시작 후 재개한 세션 1.4초
  - M6 빌드: 0.49 / 0.70 / 1.0초
  - 같은 기간 5분 평균 CPU 0.25%
  - 측정 조건: [perf.md 2차 수정](perf.md#codex-live-updates-follow-up-2026-10-09),
    [M6 확인](perf.md#regression-checks-on-the-m6-build-real-app)

**남은 한계.** 24시간 넘게 쉬었다가 재개한 세션은 5분 폴링에 의존합니다. 열린 파일에 대한 FSEvents
동작은 한 기기에서 관찰한 결과입니다.

### 사례 2. 증분 파싱과 반복 사용 성능 (M4, M6)

**문제.** M3는 로그가 바뀌면 60초마다 Claude 로그 전체(163.7MB)를 다시 읽었습니다. 그 결과 CPU 평균
2.37%, footprint 최고 208.2MB로 목표를 넘었습니다. AI가 읽기 전용 probe로 원인을 찾았습니다.
백그라운드에서 디코딩한 객체가 스캔이 끝날 때까지 해제되지 않아 약 209MB가 잡혀 있었습니다.

**선택 근거.**

- 파일별로 inode, 크기, offset을 기억해 두고 새로 추가된 바이트만 읽습니다.
- 1MB 청크마다 autorelease pool을 둡니다.
- 이벤트를 1.5초 단위로 묶어 처리합니다.
- 결과가 같으면 UI를 다시 계산하지 않습니다.
- 인덱스는 메모리에만 둡니다. 첫 스캔이 1.4초라 디스크에 저장할 필요가 없다고 기록했습니다.

**검증 결과.**

- 자동 테스트: 무작위 40가지로 나눠 덧붙여도 전체 파싱과 결과가 같은지 Claude와 Codex 각각에서
  확인합니다. 잘림, 교체, 삭제된 파일도 테스트합니다(`IncrementalIndexTests.swift`).
- M4 실측: CPU 0.31%, 최고 47.0MB, 갱신 평균 12.9ms. 기준선 측정 때보다 로그 활동이 적었던 조건
  차이가 있습니다.
- M6 반복 사용: 패널·설정·기록 창을 93회 열고 닫았습니다. footprint는 42~45MB에서 정착했고 반복할수록
  늘지 않았습니다. 수명 최고치는 48.5MB였습니다.
- 순간 메모리 문제도 측정 중에 발견했습니다. `NSPopover`는 163MB까지(PR #1), Swift Charts는 약
  100MB까지(M5) 올랐고, 둘 다 M5에서 교체했습니다.

**남은 한계.**

- 측정은 개발 기기 한 대에서만 했습니다.
- 수천 회 반복이나 며칠 연속 실행은 측정하지 않았습니다.
- Codex 온라인 조회를 켜면 합산 메모리가 약 60MB로 목표를 넘습니다.

### 사례 3. 기존 statusline을 보존하는 훅과 설정 보호 (M2)

**문제.** Claude 한도는 statusline 입력으로만 받을 수 있습니다. 그런데 작성자는 이미 서드파티 HUD
statusline을 쓰고 있었고, 이를 덮어쓰면 기존 표시가 사라집니다. 그래서 체이닝을 P0로 두었습니다.
AI가 HUD 소스를 분석한 결과는 다음과 같습니다([log-schemas §3.2](log-schemas.md)).

- command에 쉘 변수 확장이 들어 있습니다.
- 실행에 수 초가 걸릴 수 있습니다. 소스 분석으로 본 것이고 측정하지는 않았습니다.
- stdin을 EOF까지 읽습니다.

**선택 근거.**

- 원본 command는 해석하지 않고 문자열 그대로 `/bin/sh -c`로 실행합니다.
- Claude Code는 실행 중인 statusline을 취소할 수 있습니다. 그래서 캐시를 먼저 원자적으로 쓴 뒤에
  기존 명령을 실행합니다.
- stdin 바이트는 다시 직렬화하지 않고 그대로 넘깁니다.
- `settings.json`은 다음 원칙으로만 고칩니다.
  - `statusLine` 부분의 바이트만 수정합니다.
  - 수정 전에 파일 전체를 백업하고 권한을 유지합니다.
  - 깨진 JSON은 거부합니다.
- 다른 도구가 statusLine을 덮어쓰면 감지하고 복구할 수 있게 합니다.

**검증 결과.**

- 자동 테스트(`StatuslineHookTests`, `StatuslineInstallerTests`): 다음 항목을 확인합니다.
  - 캐시를 쓴 뒤에 자식 명령이 시작되는지
  - 입력 바이트가 그대로 전달되는지
  - 설치·제거 후 원래 바이트로 복원되는지
  - 깨진 설정을 거부하는지
  - 덮어쓴 상태를 감지하고 복구하는지
- 측정(release, 300회): 훅 단독 p50 5.65ms, p95 7.26ms. 자식 명령이 3초 걸려도 캐시 기록은 4.9ms에
  끝났습니다.
- 실제 환경(작성자 승인 후 개발 기기):
  - `settings.json` 변경은 `statusLine.command` 한 줄뿐이었습니다.
  - 기존 HUD 출력이 정상인 것은 작성자가 직접 봤습니다.
  - 주간 값이 캐시 24%, HUD 25%로 달랐습니다. HUD가 자체 조회값과 비교해 더 큰 값을 보여주기
    때문입니다.
- M6: 임시 프로필에서 설치 → 덮어씀 → 복구 → 제거 흐름을 다시 확인했습니다.

**남은 한계.**

- 훅이 SIGKILL을 받으면 실행 중인 기존 명령은 끝까지 실행됩니다.
- Claude Code가 실제로 보내는 취소 시그널은 확인하지 못했습니다.
- 체이닝 구간의 실행 시간은 측정하지 않았습니다.
- 복구하면 제거할 때 되돌리는 원본이 새 command로 바뀝니다(README "처음 실행").

## 4. AI 에이전트와 작업한 방식

주로 Claude Code를 썼고, 일부 작업에는 Codex를 썼습니다.

- **AI에 맡긴 일:** 마일스톤 계획 제안, 로그 형식과 조회 경로 조사, 구현, 테스트, 성능 측정, 원인
  진단, 문서와 PR 본문 작성
- **작성자가 한 일:** 요구사항과 원칙 결정, 실사용 중 문제 발견, 실제 환경에 영향을 주는 작업 승인(훅
  설치, 실제 계정 조회 진단), PR 병합 승인

코드 검증은 세 가지로 했습니다.

- **별도 리뷰 에이전트의 PR 리뷰:** #6에서 HIGH 1건과 MEDIUM 4건을 고친 뒤 재리뷰했고, #7에서
  MEDIUM 1건을 고쳤습니다.
- **자동 테스트:** 버그를 고칠 때는 재현 테스트를 먼저 추가하고, 수정 전 코드에서 실패하는지
  확인했습니다(#3, #9, #10, #14). `./scripts/test.sh`와 CI는 실제로 실행된 테스트 개수를 확인합니다.
- **작성자의 실사용 확인:** 언어 전환, 패널 닫기, 도구 켜고 끄기, 새로고침, 알림 테스트 배너를 실제
  앱에서 확인했습니다([PROGRESS](PROGRESS.md#verified-in-the-real-app)).

작업 규칙은 [CLAUDE.md](../CLAUDE.md)에 있습니다.

- 실측과 추정, 자동 테스트와 수동 확인을 구분해 기록합니다.
- 실제 `~/.claude`와 `~/.codex` 파일은 커밋하지 않습니다.
- fixture는 익명화합니다.
- 작업마다 브랜치와 PR을 만들고, 작성자가 승인한 뒤에만 squash merge합니다.
