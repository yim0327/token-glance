# 개발 기록

Token Glance를 만든 과정을 정리한 문서입니다. 왜 만들었는지, 어떤 순서로 진행했는지, 실제로
쓰면서 발견한 문제를 어떻게 확인하고 고쳤는지를 다룹니다. 요구사항 전체는 [PRD](PRD.md), 측정
수치와 조건은 [성능 기록](perf.md), 현재 상태는 [진행 상황](PROGRESS.md)에 있습니다.

## 1. 출발점과 초기 제약

작성자는 Claude Code와 Codex CLI를 구독 플랜으로 함께 씁니다. 남은 한도를 보려면 도구마다
터미널에서 `/usage`나 `/status`를 따로 확인해야 했습니다. 두 도구의 남은 %와 초기화 시각을 메뉴바에
나란히 띄워 두고 싶다는 것이 출발점입니다.

첫 커밋에 들어간 PRD 초안(v0.4)은 작성자가 AI 코딩 도구 Claude Code와 대화하며 만들었습니다.
화면에 무엇을 보여줄지와 프라이버시 원칙은 작성자가 정했습니다. 프라이버시 원칙은 프롬프트·응답
내용을 저장하지 않고, 기본 설정에서 네트워크 호출을 하지 않으며, 인증 정보를 직접 읽지 않는
것입니다. 성능 목표는 AI가 제안한 수치를 작성자가 받아들였습니다. 목표는 idle CPU 1% 미만, 메모리
50MB 미만, 증분 갱신 200ms 미만, 훅 실행 20ms 이하입니다.

처음부터 정해져 있던 제약은 다음과 같습니다.

- 구독 한도는 토큰 수가 아니라 %로만 노출됩니다. Claude Code 로컬 로그에는 이 %가 없어서
  statusline 훅으로 받아야 합니다.
- 로그와 훅 입력의 형식은 공개된 규격이 아닙니다. 그래서 PRD에서 검증 대상으로 표시한 가정을 실제 로컬
  데이터로 먼저 확인하고 [log-schemas.md](log-schemas.md)에 기록한 뒤 구현하기로 했습니다.
- Apple Developer 계정이 없습니다. 첫 배포는 ad-hoc 서명, 미공증, arm64 전용 zip입니다.
- `~/.claude/settings.json`은 사용자 동의를 받고 백업을 남긴 뒤에만 바꿉니다.

[PRD §12](PRD.md#12-마일스톤)를 줄인 것이고, "실제 진행"에는 계획과 달라진 점을 적었습니다.

## 3. 문제 해결 사례

### 사례 1. Codex 사용량 갱신 누락 ([#1](https://github.com/yim0327/token-glance/pull/1), [#3](https://github.com/yim0327/token-glance/pull/3))

**문제.** 작성자가 Codex를 쓰는 동안 메뉴바의 Codex 값이 바뀌지 않는 것을 발견해 알렸습니다.
새로고침을 누르면 값이 바뀌었습니다.

**확인 방법.** AI가 진단용 probe를 만들어 단계별 지연을 나눠 봤습니다. probe는 시각, 이벤트 종류,
바이트 수, 줄 종류만 기록하고 내용은 기록하지 않았습니다. 확인된 내용은 다음과 같습니다.

- Codex는 rollout 파일을 열어 둔 채 계속 덧붙입니다.
- 이 기기의 FSEvents는 파일 생성만 알리고, 이후 덧붙인 내용은 알리지 않았습니다.
- 그래서 기록 36초 뒤에야 5분 폴링으로 반영됐습니다. 증분 읽기 자체는 약 20ms였습니다.

1차 수정 후 작성자가 다시 누락을 발견했습니다. 새 세션, 그리고 앱 재시작 뒤 재개한 세션에서
빠졌습니다. 이 두 경우는 작성자가 Codex를 직접 실행해 재현했습니다. AI는 아닌 원인도 하나씩
확인해 기록했습니다(경로, 날짜 폴더, 로그 구조, 읽기 offset, UI, 중복 실행).

**선택 근거.** 덧붙임을 감지하는 방법으로, 최근 커진 rollout만 2초마다 `stat`으로 크기를 비교하게
했습니다. 크기가 바뀐 경우에만 기존 증분 읽기 경로를 실행하므로 전체 재파싱은 하지 않습니다.
2차 수정에서는 감시 대상을 넓혔습니다. 첫 스캔 이후 새로 생긴 파일과 24시간 안에 수정된 rollout도
감시합니다.

**검증 결과.**

- 자동 테스트: `ActiveFileSetTests`의 회귀 테스트 2개가 수정 전 코드에서 실패하는 것을 먼저
  확인했습니다. `IncrementalIndexTests`에는 "첫 동기화 뒤 생긴 세션이 조각나 커져도 전체 파싱과
  결과가 같다"는 테스트를 추가해 무작위 20가지 분할로 돌립니다.
- 실사용 측정:
  - 1차 수정 후 반영 시간은 1.8, 0.4, 0.2초였습니다.
  - 2차 수정 후에는 새 세션 0.03초, 최근 세션 1.4초, 재시작 후 재개한 세션 1.4초였습니다.
  - M6 빌드에서 다시 확인했을 때는 0.49 / 0.70 / 1.0초였습니다.
  - Codex를 쓰는 5분 동안 CPU는 평균 0.25%였습니다.
- 세부 내용: [perf.md](perf.md#codex-live-updates-2026-10-09)

**남은 한계.** 24시간 넘게 쉬다가 재개한 세션은 5분 폴링에 의존합니다. 열린 파일에 대한 FSEvents
동작은 한 기기에서 관찰한 것으로, Apple이 문서로 보장한 동작이 아닙니다.

### 사례 2. 증분 파싱과 반복 사용 성능 (M4, M6)

**문제.** M3에서는 로그가 바뀌면 60초마다 Claude 로그 전체(72개 파일, 163.7MB)를 다시 읽었습니다.
5분 측정에서 CPU는 평균 2.37%, footprint 최고치는 208.2MB로 목표를 넘었습니다. 증분 갱신은 처음
계획부터 M4 작업이었습니다.

**확인 방법.** AI가 번들된 release 앱을 5분씩 실행하며 측정했습니다. CPU는 `ps` CPU 시간 증분,
메모리는 `footprint`와 `vmmap`으로 쟀습니다. 메모리가 높았던 원인을 찾으려고 읽기만 하는 probe를
따로 돌렸고, 약 209MB가 잡혔습니다. 백그라운드 스레드에서 디코딩한 객체가 스캔이 끝날 때까지
해제되지 않았기 때문입니다.

**선택 근거.**

- 파일별 inode, 크기, byte offset을 기억해 두고 새로 추가된 바이트만 읽습니다.
- 1MB 청크마다 autorelease pool을 둡니다.
- FSEvents 이벤트를 1.5초 단위로 묶고, 관련 파일의 이벤트만 반영합니다.
- 결과가 같으면 UI를 다시 계산하지 않습니다.
- 인덱스는 메모리에만 둡니다. 현재 규모에서는 앱 시작 시 첫 스캔이 1.4초라 저장해 둘 필요가
  없다고 기록했습니다.

**검증 결과.**

- 자동 테스트: 무작위로 나눠 덧붙인 결과가 전체 파싱과 같은지 Claude와 Codex 각각 40가지 분할로
  확인합니다. 미완성 마지막 줄, 잘림·교체·삭제된 파일도 테스트합니다
  (`IncrementalIndexTests`).
- M4 실측: CPU 0.31%, footprint 최고 47.0MB, 갱신 평균 12.9ms. 다만 측정 구간의 로그 활동이
  기준선보다 적었다는 조건 차이가 있습니다.
- M6 반복 사용(측정 전용 빌드): 상세 패널, 설정 창, 기록 창을 각각 30회씩 열고 닫았습니다(총 93회,
  22분). footprint는 42~45MB에서 정착했고 반복할수록 늘지 않았습니다. 수명 최고치는 48.5MB였습니다.
- 다른 측정 중에 순간 메모리 문제도 발견했습니다. Codex 진단 측정(PR #1)에서는 `NSPopover`를 열
  때 163MB까지 올랐고, M5에서는 Swift Charts가 다시 그릴 때마다 약 100MB를 잡았습니다. M5에서 각각
  테두리 없는 패널과 기본 도형 차트로 바꿨습니다.

**남은 한계.** 측정은 개발 기기 한 대에서 했습니다. 수천 회 반복이나 며칠 연속 실행은 측정하지
않았습니다. Codex 온라인 조회를 켜면 자식 프로세스를 포함한 메모리가 약 60MB로 50MB 목표를
넘습니다([PROGRESS](PROGRESS.md)).

### 사례 3. 기존 statusline을 보존하는 훅과 설정 보호 (M2)

**문제.** Claude의 한도 %는 statusline 입력으로만 받을 수 있어서 `statusLine`에 훅을 등록해야
합니다. 그런데 작성자는 이미 서드파티 HUD statusline을 쓰고 있었습니다. 훅이 이를 덮어쓰면 기존
표시가 사라지므로 체이닝을 P0로 두었습니다.

**확인 방법.** AI가 그 HUD의 설정과 소스를 분석했습니다([log-schemas §3.2](log-schemas.md)).
확인한 내용은 세 가지입니다.

- command에 쉘 변수 확장이 들어 있습니다.
- 네트워크 대기 때문에 실행이 수 초까지 걸릴 수 있습니다. 이 부분은 소스 분석으로 본 것이고
  측정하지는 않았습니다.
- stdin을 EOF까지 읽습니다.

Claude Code는 실행 중인 statusline을 다음 업데이트가 오면 취소할 수 있다는 점도 함께 고려했습니다.

**선택 근거.** 관찰한 내용마다 대응 규칙을 정했습니다.

- 원본 command는 해석하지 않고 문자열 그대로 저장해 `/bin/sh -c`로 실행합니다.
- 캐시를 먼저 원자적으로(임시 파일 → rename) 쓰고, 그다음에 기존 명령을 실행합니다.
- 받은 stdin 바이트는 다시 직렬화하지 않고 그대로 넘긴 뒤 닫습니다.
- `settings.json`은 `statusLine` 부분의 바이트만 고칩니다. 수정 전에 파일 전체를 백업하고 원래
  권한을 유지합니다. 깨진 JSON이나 쓸 수 없는 파일이면 아무것도 바꾸지 않습니다.
- 다른 도구가 statusLine을 다시 덮어쓰면 이를 감지해 알리고, 복구할 수 있게 합니다.

**검증 결과.**

- 자동 테스트(`StatuslineHookTests`, `StatuslineInstallerTests`):
  - 자식보다 캐시 기록이 먼저 끝나는지
  - 입력 바이트가 바뀌지 않고 전달되는지
  - 설치하면 command만 바뀌고, 제거하면 원래 바이트로 돌아오는지
  - 깨진 설정을 거부하는지
  - 덮어쓴 상태를 감지하고 복구하는지
- 측정(release 빌드, 300회): 훅 단독 p50 5.65ms, p95 7.26ms. 자식 명령이 3초 걸리는 경우에도
  캐시 기록은 4.9ms에 끝났습니다.
- 실제 환경(작성자가 설치를 승인한 뒤 개발 기기에서):
  - `settings.json`에서 바뀐 것은 `statusLine.command` 한 줄뿐이었습니다.
  - 훅이 캐시를 기록했고, 기존 HUD 출력이 정상인 것은 작성자가 직접 봤습니다.
  - 주간 값이 HUD는 25%, 캐시는 24%로 1%p 달랐습니다. HUD가 자체 조회값과 입력값 중 큰 쪽을
    보여주기 때문입니다.
- M6: 임시 프로필에서 설치 → 덮어씀 → 복구 → 제거 흐름을 다시 확인했습니다. 실제
  `settings.json`은 바뀌지 않았습니다.

**남은 한계.**

- 훅이 SIGKILL을 받으면 이어서 실행 중인 기존 명령은 끝까지 실행됩니다. Claude Code가 실제로
  보내는 취소 시그널은 확인하지 못했습니다.
- HUD를 포함한 체이닝 구간의 실행 시간은 측정하지 않았습니다.
- 복구(repair)를 하면 제거할 때 되돌릴 원본이 덮어쓴 새 command로 바뀝니다(README '처음 실행').

## 4. AI 에이전트와 작업한 방식

**AI에 맡긴 일.** 주로 Claude Code를 썼고, 일부 작업에는 Codex를 썼습니다. 맡긴 일은 다음과
같습니다.

- 마일스톤 계획 제안
- 로그 형식과 조회 경로 조사
- 구현, 테스트 작성, 성능 측정, 원인 진단
- 문서와 PR 본문 작성

코드 리뷰는 별도의 리뷰 에이전트가 했습니다. PR #6에서는 HIGH 1건과 MEDIUM 4건을 찾아 고친 뒤 다시
리뷰했고, PR #7에서는 MEDIUM 1건을 고쳤습니다.

**작성자가 한 일.**

- 요구사항과 원칙을 정했습니다.
- 실사용 중 문제를 발견해 알렸습니다.
- 실제 앱을 직접 확인했습니다. 언어 전환, 패널 닫기, 도구 켜고 끄기, 새로고침, 알림 테스트 배너
  등입니다([PROGRESS](PROGRESS.md#verified-in-the-real-app)).
- 실제 환경에 영향을 주는 작업을 승인했습니다. 개발 기기에 훅을 설치하는 것과 실제 계정 조회
  진단을 실행하는 것입니다.
- PR 병합을 승인했습니다.

작성자는 코드 리뷰를 거의 하지 않았습니다.

**검증을 기록으로 남기는 규칙.** 사람이 코드를 읽는 대신, 결과를 기록으로 확인할 수 있도록 작업
규칙([CLAUDE.md](../CLAUDE.md))을 두었습니다.

- 완료를 보고하기 전에 `./scripts/test.sh`로 실제 실행된 테스트 개수를 확인합니다. CI도 테스트
  개수를 확인합니다.
- 버그를 고칠 때는 재현 테스트를 먼저 추가하고, 수정 전 코드에서 실패하는지 확인합니다(#3, #9,
  #10, #14).
- 실측과 추정, 자동 테스트와 수동 확인을 구분해 적습니다([perf.md](perf.md), [PROGRESS](PROGRESS.md)).
- 실제 `~/.claude`와 `~/.codex` 파일은 커밋하지 않고, fixture는 익명화합니다. 진단 probe는 시각과
  바이트 수 같은 수치만 기록합니다.
- 작업마다 새 브랜치와 PR을 만들고, 작성자가 승인한 뒤에만 squash merge합니다.
